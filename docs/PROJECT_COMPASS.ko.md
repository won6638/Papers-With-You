# CiteWeave 프로젝트 기준서

문서 버전: 0.1 / 작성일: 2026-09-30 (한국 시간) / 대상 프로그램: 0.1.0a1 비공개 알파

이 문서는 사용자와 이후 작업을 맡는 개발자·AI가 공유하는 프로젝트의 기준점이다. 실행 방법은 README, 실제 동작의 근거는 소스와 테스트, 검증 이력은 VERIFICATION을 함께 읽는다. 문서에 적힌 미래 기능을 현재 기능으로 설명하지 않는다. 사용자 피드백 전의 제안은 확정 요구사항으로 바꾸지 않는다.

## 1. 프로젝트의 목적과 현재 위치

CiteWeave는 사용자의 분야와 관심을 바탕으로 필요한 학술 자료를 찾고, 승인된 자료를 로컬에 신뢰성 있게 보관하며, 장기적으로 지식 탐색·추천·질의응답에 활용하는 프로젝트다. 보편적 지식 저장소를 지향하지만, 현재 자료 유형과 구현 범위는 arXiv 논문으로 좁힌다. 모든 분야·모든 문서 형식을 이미 지원하는 제품은 아니다.

핵심 문제는 세 가지다. 첫째, 검색되는 논문과 실제로 다운로드되는 논문은 다르다. 둘째, 너무 많은 결과에서 무엇을 읽을지 선택하기 어렵다. 셋째, 정적인 학습용 데이터셋만으로는 최신 논문을 반영하기 어렵다. 따라서 수집의 신뢰성과 관측 가능성을 먼저 만들고, 관련성 평가와 추천을 그 위에 추가한다.

현재 알파는 **사용자 조건으로 arXiv를 검색하고, 후보를 보여주고, 승인받은 PDF를 검증·저장하는 로컬 CLI**다. 개인화 추천 모델이나 범용 지식 검색 엔진은 아직 아니다. 검색 결과 정렬은 최근 수정 순이며, 사용자의 만족도나 전문성을 학습하지 않는다.

저장소: https://github.com/won6638/CiteWeave — 현재 Private, 기본 브랜치 main. 초기 28개 파일 업로드를 완료했고 Windows 출력 인코딩 수정 및 회귀 테스트를 반영했다. 최초 원격 구현 기준 커밋은 `5c683db5fc0ac6ac2a2db33e271ed234363df4a3`이다. 이 기준서 및 후속 문서 수정은 그 이후 커밋으로 관리한다.

## 3. 현재 사용자 흐름

1. Python 3.12 가상환경을 만들고 requirements.txt를 설치한다.
2. `python citeweave.py init`으로 설문에 응답해 로컬 JSON 프로필을 만든다.
3. `search`로 후보만 확인하거나 `run`으로 검색부터 승인·수집까지 진행한다.
4. 후보 번호, 범위 또는 all로 선택한다. 일반적인 대화형 실행에서는 추가 y/N 확인을 받는다. 빈 선택은 취소다.
5. 승인한 각 논문을 순차 다운로드한다. 파일 형식과 구조를 검증한 뒤 최종 경로로 옮긴다.
6. 실패는 기록하고 나머지 항목을 처리한다. `status`로 실행 상태를 보고 `resume`으로 같은 실행을 재개한다.
7. 새 논문 후보가 필요하면 `sync`로 제한된 재검색을 수행한다. 자동 백그라운드 실행은 없다.

처음에는 카테고리 코드를 직접 입력해야 한다. 예: cs.AI, cs.LG. 자연어 분야 이름을 자동으로 코드에 연결하는 기능은 없다. 한국어 자유 설명을 저장할 수 있지만 한국어 설명을 영어 검색식으로 번역하거나 의미적으로 해석하지 않는다.

## 4. 명령행 인터페이스 명세

| 명령 | 하는 일 | 주요 옵션·주의 |
|---|---|---|
| `--version` | 프로그램 버전 출력 | 현재 0.1.0a1 |
| `init` | 대화형 설문과 프로필 저장 | `--profile`; 기존 파일은 덮어쓰기 확인 |
| `search` | 검색, 후보·메타데이터·실행 기록 저장 | `--profile`, `--output`; PDF는 받지 않음 |
| `run` | 검색 후 선택·승인·수집 | `--profile`, `--output`, `--select`, `--yes` |
| `sync` | 같은 조건으로 새 실행을 만들어 제한 재검색·수집 | run과 같은 옵션. 완전한 증분 동기화 아님 |
| `resume` | 기존 run의 승인된 작업 재개 | `--run-id` 필수, `--output`, `--select`, `--yes` |
| `status` | 저장소의 최근 실행 최대 20개 표시 | `--output`; 개별 논문 상세 대시보드 아님 |

`--select 1,3-5`는 후보 1, 3, 4, 5를 선택한다. `--yes`만 주면 현재 후보 전부를 승인한다. `auto_download=true`도 기본적으로 모든 후보를 선택하고 확인을 생략한다. `search`는 이러한 옵션과 관계없이 PDF를 다운로드하지 않는다.

비대화형 실행은 자동 승인 없이 다운로드하지 않는다. `resume`에 이전 승인 항목이 있고 새 선택이 없으면 이전 승인을 재사용한다. `resume --select`는 기존 승인 집합에 추가하며 이전 승인을 취소하는 기능이 아니다. 사용자 지정 저장 위치를 썼다면 resume/status에도 동일한 `--output`을 줘야 한다.

종료 코드: 0은 정상 완료 또는 목록만 저장, 1은 작업 오류, 2는 수집 중 일부 실패, 130은 키보드 중단이다. argparse 인자 오류도 2를 사용할 수 있으므로 운영 자동화는 종료 코드만으로 실패 종류를 완전히 구분하지 말고 기록을 함께 본다.

## 5. 프로필 입력 스키마 v1

| 필드 | 형식·기본값 | 실제 반영 방식 |
|---|---|---|
| categories | 문자열 목록, cs.AI / cs.LG | 카테고리 OR. 코드 형식 검사는 하지만 실제 존재하는 카테고리 사전 검증은 없음 |
| keywords | 문자열 목록, 빈 목록 | 모든 필수 구문 AND, arXiv all 필드 검색 |
| exclude | 문자열 목록, 빈 목록 | ANDNOT으로 제외 |
| since / until | 날짜 문자열, 빈 값 | 최초 제출일 범위, YYYY-MM-DD. 수정일 필터가 아님 |
| max_results | 정수 20, 허용 1–100 | 전체 학술 데이터가 아니라 이번 후보 수 상한 |
| purpose | 문자열 research | 저장만 함. 순위·검색에 영향 없음 |
| description | 문자열, 빈 값 | 로컬 저장만 함. LLM에 전송하지 않음 |
| output_dir | 문자열, 빈 값 | 빈 값은 런처 옆 downloads |
| contact | 문자열, 빈 값 | 선택 입력. User-Agent에 포함되어 공급처에 전달됨 |
| auto_download | 불리언 false | 명시적 자동 승인 설정 |
| max_file_mb | 정수 50, 허용 1–250 | 논문 파일당 MiB 상한 |
| max_total_mb | 정수 250, 허용 1–1000 | 수집 시 공유 수신 바이트 카운터에 적용하는 MiB 상한 |
| ids | 문자열 목록, 빈 목록 | 정확한 arXiv ID 진단 모드. 다른 검색 조건을 대체 |
| schema_version | 정수 1 | 다른 버전은 거부 |

각 목록은 최대 100개 항목이며 빈 문자열 항목은 허용하지 않는다. 키워드·제외 구문은 각 500자 이하, 따옴표·역슬래시·줄바꿈을 제한한다. contact는 200자 이하이며 줄바꿈을 허용하지 않는다. 자유 설명 전체 길이 제한·계층형 관심 분야·사용자별 계정은 아직 없다.

일부 필드(상한, ids, auto_download)는 설문에서 직접 묻지 않으므로 JSON을 편집한다. 프로필에서 지정한 상대 저장 경로는 프로필 파일의 폴더 기준이고, CLI `--output` 상대 경로는 실행한 셸의 현재 폴더 기준이다.

바이트 예산의 정확한 현재 동작: 같은 Client가 검색과 PDF 수집의 수신량을 누적한다. run/sync에서는 앞선 Atom 수신 바이트도 수집 예산 판정에 포함되며, PDF 재시도 바이트도 누적된다. search 단계 자체에는 이 총량 상한을 아직 설정하지 않고 응답당 4 MiB 상한을 사용한다. resume은 새 세션 카운터로 시작한다. 저장소 전체 디스크 용량 상한은 아니다. 수신 후 검사하므로 한 read 블록(64 KiB)만큼 초과할 수 있다.

## 6. 검색·다운로드·검증 동작

### 검색

HTTPS arXiv Atom API에 요청한다. 한 페이지는 최대 50개, 총 후보 최대 100개다. `lastUpdatedDate` 내림차순을 요청한다. 같은 공급처·ID·버전 키를 중복 제거한다. 검색은 검색 인덱스에 의존하며 모든 최신 논문을 즉시 얻는다는 보장은 없다. XML DOCTYPE/ENTITY를 거부하고 Atom 구조·논문 식별자·버전 형식을 확인한다. 원시 feed 임시파일은 처리 후 삭제한다.

### 전송

허용 호스트는 arxiv.org, export.arxiv.org, www.arxiv.org이며 HTTPS 및 허용 포트를 검사한다. 리디렉션에도 같은 검사 적용. 동시 대량 다운로드 대신 직렬 처리하고 같은 OS 사용자 내 요청을 파일 잠금으로 조정한다. 각 요청 완료 후 다음 요청까지 최소 3.1초 간격을 둔다. 다른 계정·기기·프로그램의 요청량은 조정하지 못한다.

소켓 timeout은 20초, 전송 루프의 경과시간 검사 기준은 60초다. 이는 DNS·파서·전체 실행을 강제로 60초 안에 중단하는 보장이 아니다. 최대 3회 시도하며 408/429/500/502/503/504, 일부 네트워크 실패, 잘린 응답·전송 시간 초과를 재시도한다. 기본 재시도 대기는 2초, 4초이며 Retry-After가 더 길면 반영한다. 60초보다 긴 Retry-After는 일찍 재시도하지 않고 실패로 남긴다. 404는 자동 재시도하지 않지만 나중에 resume으로 다시 시도할 수 있다.

### PDF 검증과 최종 저장

`%PDF-` 헤더, pypdf strict 파싱, 비암호화 여부, 1개 이상의 페이지, 페이지 내용 스트림 읽기를 확인한다. SHA-256, 파일 바이트 수, 페이지 수를 메타데이터에 저장한다. 다운로드는 `.part`로 받고 검증 성공 후 `os.replace`로 최종 PDF를 바꾼다. 기존 파일이 손상된 경우 대체본이 검증될 때까지 기존 파일을 유지한다.

이는 악성코드 검사, PDF 렌더링 검증, 저자·내용 진위 검증, 논문 원문과의 의미 일치 검증이 아니다. 파서는 별도 샌드박스에 격리되어 있지 않고 파싱 시간·메모리 상한도 없다. 파일은 자동으로 열지 않는다. 암호화되었거나 엄격한 파서가 거부하는 PDF는 사람이 열 수 있더라도 실패할 수 있다.

### 복구·버전

논문 키는 provider:paper_id:version이다. 수정본마다 별도 폴더를 사용하므로 v2가 v1을 덮어쓰지 않는다. 저장된 PDF를 재검증하고 기존 체크섬과 비교해 cached로 재사용한다. 최종 PDF 이동 후 DB 기록 전 중단된 파일은 재검증해 recovered로 등록할 수 있다. 미완료 PDF는 처음부터 다시 받으며 HTTP Range 이어받기는 없다. 디스크 손상·DB 파손에 대한 백업 복원 기능은 없다.

## 7. 저장 구조와 데이터 계약

| 위치 | 내용 |
|---|---|
| profiles/default.json | 기본 설문 프로필; Git 추적 제외 |
| downloads/state.sqlite3 | runs, papers, jobs, artifacts 테이블 |
| downloads/papers/IDvN/paper.pdf | 버전별 최종 PDF. 구형 arXiv ID의 /는 _로 변환 |
| downloads/papers/IDvN/metadata.json | 공급처, ID·버전, 제목, 저자, 초록, 분야, 최초 제출·수정 시각, URL, DOI, 검증 결과 |
| downloads/runs/RUN_ID/profile.json | 해당 실행 설정 스냅샷 |
| downloads/runs/RUN_ID/candidates.json | 후보, 공급처 보고 전체 수, 잘림 가능성 표시 |
| downloads/runs/RUN_ID/events.jsonl | 세션별 시간·이벤트 누적 기록 |
| downloads/runs/RUN_ID/papers.csv | 후보 번호·키·제목·선택·현재 상태·실패 사유 |
| downloads/runs/RUN_ID/summary-SESSION_ID.json | 개별 세션 집계 |
| downloads/runs/RUN_ID/summary.json | 가장 최근 세션 집계 |

DB가 작업 상태의 기준이다. profile/candidates는 입력 당시 정보를 보존하며 CSV와 summary는 재실행 후 바뀔 수 있다. metadata.json의 검증 시각은 재검증 때 갱신된다. 데이터 스키마 마이그레이션 도구는 아직 없다. 현재 테이블 생성은 user_version=1을 사용하며 향후 DB 변경에는 별도 이전 설계가 필요하다.

메타데이터 license_url 필드는 있지만 현재 Atom 파서는 논문별 라이선스를 추출하지 않아 일반적으로 null/unknown이다. `identity_status=provider_link_only`는 공급처 URL 기반 식별이라는 뜻이다. 메타데이터에 DOI가 있더라도 DOI 기반 공급처 간 통합은 없다.

job 상태는 candidate, pending, downloading, complete, cached, recovered, failed다. 실행 상태에는 running, preview, complete, partial, failed, interrupted가 있다. resume은 같은 run ID에 새 session ID를 추가한다.

## 8. 로그와 측정값을 읽는 방법

UTC 시각, run/session ID, 소프트웨어 버전, 패키지 소스 지문, Python/pypdf 버전, 단계별 시간, 요청 호스트·상태·시도 번호, 바이트 수, 실패 원인과 대기를 기록한다. 소스 지문은 citeweave 패키지의 .py 파일을 대상으로 하며 전체 Git 커밋 해시의 대체물이 아니다.

| 지표 | 의미와 해석 제한 |
|---|---|
| elapsed_s | 현재 세션 경과 시간. 이전 resume 세션까지 합친 시간이 아님 |
| selected_count / valid_selected_count | 현재 run에서 승인된 항목 및 complete/cached/recovered 항목 수 |
| acquisition_ratio | 승인된 항목 중 현재 확보된 비율. 캐시·복구도 포함 |
| download_validation_ratio | 이번 세션에서 다운로드를 시도한 논문 중 complete 비율. 캐시만 쓰면 null |
| request_count / bytes_received | 현재 세션 요청 수·받은 바이트. 검색과 재시도가 포함될 수 있음 |
| request_p50_s / request_p95_s | 작은 표본에서 계산한 요청 소요시간 요약. 통계적 신뢰도나 SLA를 뜻하지 않음 |
| rate_wait_s / retry_wait_s | 요청 간격 대기 및 재시도 대기 기록의 합 |
| job_status_counts | 과거 세션을 포함해 갱신된 해당 run의 현재 작업 상태 |

events 로그에 검색 쿼리나 요청 헤더를 복사하지 않지만, 프로필에는 관심 분야·자유 설명·선택 연락처가 들어가고 후보에는 관심 논문 정보가 들어간다. 모든 출력물이 익명이라는 뜻이 아니다. 기본 동작은 로컬 보관이며 외부 분석·텔레메트리 서버는 없다. 검색어와 contact User-Agent는 실제 공급처 요청에 사용된다.

## 11. 검증 결과와 작업 이력

초기 로컬 검증은 Ubuntu 24.04.3, Python 3.12.14에서 19개 테스트, README 대응 검사, 컴파일, wheel 빌드를 통과했다. 이후 Windows CI에서 출력 인코딩 문제가 발견되어 sys.stdout/sys.stderr의 기존 인코딩을 유지하면서 표현 불가능한 글자는 backslashreplace로 출력하도록 수정했다. 회귀 테스트 포함 현재 20개 테스트가 로컬에서 통과한다. UTF-8을 지원하지 않는 출력 환경에서는 한글이 이스케이프 형태로 보일 수 있지만 프로그램은 그 이유로 중단되지 않는다.

CI는 외부 arXiv에 접속하지 않는다. 3개 환경에서 테스트·README 검사 통과는 실제 인터넷 다운로드·데스크톱 UI·모든 잠금 경합을 검증한 것이 아니다. 현재 테스트는 XML/URL/프로필·선택 검증, HTML 오인 방지, 429/404, 크기 제한, 캐시·손상·복구·중단·버전, 비대화형 승인, 로그 노출 및 출력 인코딩을 다룬다. 다중 프로세스 잠금 경합, 디스크 부족, 대규모 PDF, 장시간 운용은 별도 시험이 필요하다.

원격 28개 파일의 경로 존재와 CI 성공은 확인했다. 브라우저 ZIP 다운로드가 완료되지 않았고 원시 다운로드 경로에는 브라우저 정책 제한이 있었다. 따라서 원격 전체를 다시 내려받아 바이트 단위로 동일성을 검증했다고 주장하지 않는다. 웹 복사 기반 대조의 일부 결과는 비동기 완료 시점 때문에 유효한 검증 근거로 사용하지 않는다. 후속 인증된 git clone 이후 해시 비교를 권장한다.

로컬 초기 commit 745d2ed의 이력을 원격으로 그대로 push한 것이 아니라 브라우저에서 파일 스냅샷을 커밋했다. 두 저장소의 이력은 다르므로 후속 작업은 원격 main을 새로 clone해서 시작한다. 로컬 초기 bundle은 이전 상태 보관용이다. 무관한 이력을 강제 push하거나 덮어쓰지 않는다.

## 13. 데이터셋·추천·최신성의 장기 설계

사용자가 제시한 S2ORC/peS2o, RedPajama/Pile의 arXiv subset, PMC Open Access, unarXive는 **후보 목록**이다. 초기 프로그램은 어떤 것도 다운로드·임베딩·학습에 사용하지 않는다. 특정 릴리스 채택, 최신 배포 현황·정확한 권리·비용 검토는 후속 결정이다.

권장 설계안은 정적 코퍼스와 최신 공급처 검색을 분리해서 함께 쓰는 것이다. 정적 코퍼스는 초기 주제 표현·관련성 평가·그래프 구조의 후보 자원이 되고, 최신 검색은 새 논문을 공급한다. 두 경로를 DOI/arXiv ID·버전·출처로 통합하고 최신 논문도 제목·초록 기반으로 평가할 수 있어야 한다. 오래된 데이터셋만으로 후보를 제한하지 않는다.

콜드스타트도 구분한다. 새 사용자는 설문·명시적 피드백으로 요구를 파악하고, 새 논문은 텍스트·메타데이터로 평가한다. 코퍼스가 크다고 사용자 취향 정답이 생기지는 않는다. 초반에는 최근순/키워드 점수 같은 설명 가능한 기준과 소수 사람이 평가한 관련성 목록을 만든 뒤 의미 검색을 비교한다.

KG는 논문·저자·분야·인용 관계와 출처를 표현하는 후보 구조다. GNN은 충분한 그래프·평가 데이터가 생긴 뒤 비교할 모델 후보이지 반드시 첫 추천 모델이어야 하는 것은 아니다. RAG는 수집과 별도로 권리 확인, 본문 추출, 청킹, 검색, 답변 인용·근거 검증을 필요로 한다. LLM 입력 해석은 자연어를 검증 가능한 프로필로 변환하고 사용자에게 결과 조건을 보여주는 방향으로 설계한다. 모델이 생성한 조건으로 곧바로 무승인 다운로드하는 것으로 해석하지 않는다.

공급처 후보 S2AG/OpenAlex 등은 논문 식별·인용 관계 확대에 대한 향후 검토 대상이다. 무료·유료 API 비교는 도입 직전에 요청 한도, 업데이트 지연, 가용성, 메타데이터 품질, 상업 이용 조건, 고정비·종량비를 표로 검토한다. 지금은 유료 계정·키·구독·결제 설정이 없다.

표의 지표·완료 조건은 제안이다. 성공률 목표 숫자, 시험 표본 수와 기간은 아직 합의하지 않았다. 기능을 많이 붙이는 것보다 신뢰할 수 있는 측정과 실패 처리에 우선순위를 둔다.

## 16. 다음 작업자 인수인계와 문서 유지 규칙

1. 원격 저장소가 여전히 Private인지와 main HEAD를 확인한다. 인증된 git clone을 사용할 수 있다면 새 clone을 기준으로 시작한다.
2. 프로젝트 기준서, README, 검증 기록과 관련 코드를 확인한다. 이전 기록만으로 현재 구현 상태를 단정하지 않는다.
3. 현재 요구와 구현을 구분한다. 보이지 않는 테스트 결과·지원 환경·다운로드 성공을 추정하지 않는다.
4. 변경 전후 소스 버전과 검증 환경을 남긴다. 필요한 테스트만 실행하고 arXiv 실제 시험은 요청 간격과 시험 예산을 준수한다.
5. 사용자에게 영향을 주는 변경은 README 양쪽과 이 기준서에 동시에 반영한다. 자동 README 비교는 번역 의미 일치를 완전히 보장하지 않으므로 의미 검토도 한다.
6. 결정이 바뀌면 기존 이유를 지우지 말고 결정 ID, 날짜, 변경 이유, 영향, 승인 상태를 기록한다.
7. 작업 종료 때 현재 상태·완료 근거·미해결 항목·다음 시작점을 갱신한다. PDF·개인 프로필·원시 로그·인증정보는 커밋하지 않는다.
